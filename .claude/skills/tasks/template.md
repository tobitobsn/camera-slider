# PROJ-X Tasks

> Generated by `/tasks` from `spec.md` + `design.md`. This is the ordered, traceable build plan — the bridge between the contract (WHAT) and the build (HOW).
> `[P]` = parallelizable: the task's files are disjoint from every other `[P]` task in the same level, so `/build` can fan it out to its own subagent.
> Levels run **sequentially** (each is a barrier). Tasks **within** a level run in parallel where marked `[P]`. Each task references the AC-IDs from `spec.md` it fulfills — that is the AC → Task → Test traceability chain.
> `[user]` = a setting only the user can make, in a provider's dashboard: `where:` instead of `files:`, never `[P]`, ticked by the user — `/build` hands it over, `/deploy` will not ship while it is open.
> `[user go-live]` = the same, but it needs the production URL or the host (a webhook endpoint and its secret, a redirect URI, an allowed origin): nobody can make it before `/deploy`, so it never blocks `/qa` or Approved — `/deploy` makes it in Step 2 and ticks it in Step 4, once the callback was seen to arrive.
> Owner: `/tasks` creates this file; `/build` checks the boxes off — except `[user]` tasks, which the user ticks.
> No status field here — the checked boxes below are this file's progress, and the feature's status lives ONLY in `features/INDEX.md`.
> Task titles are written in the project's working language (`CLAUDE.md` → Key Conventions); file paths, table and route names stay as they are in the code. The examples below are English — translate the wording, not the paths.

## Parallelization

- **Levels are barriers.** A level only starts once the previous level is fully integrated and verified against its AC-IDs. This keeps the data contract ahead of the UI: schema (L1) → API (L2) → UI (L3).
- **`[P]` requires disjoint files.** Two `[P]` tasks in the same level may never list the same path under `files:`. If they would touch the same file, they are **not** both `[P]` — sequence them (drop `[P]` from one) or merge them into one task.
- **Coarse-grained, not micro — and never larger than one sub-agent's context.** Tasks are meaningful checkpoints (~5–20 per feature), not single-line edits; one concern and about five files at most, split beyond that.
- **`[user]` tasks are never parallel and never built.** They sit in the level whose code depends on them; `/build` prints the hand-off (what, where, which value) when it reaches the level and carries on — the box stays open until the user ticks it. A `[user go-live]` box stays open until `/deploy` has made the setting and seen it work.
- During `/build`, each `[P]` task in the active level runs in its own subagent with an isolated git worktree, then the main agent integrates, verifies against the level's AC-IDs, and checks the boxes here. Subagents never declare themselves done — there is one verification owner.
